Task artifacts and linking

Plans, prompts and reviews are artifacts of the task. They live in PageSpace, where page history versions them, and they are connected to tasks with @-mentions so they can be retrieved from either side. Local temp directories are scratch and are never the record.

Where things live

  • {{page:roadmap}} — the board only: Epic → Phase → Leaf. A task page holds its acceptance criteria and a "Related pages" block. No documents are filed under task pages.
  • {{page:plans}}/<Epic> — specifications, delivery maps, preparation plans, delivery logs and builder handoffs.
  • {{page:prompts}}/<Epic> — task-specific prompts: one page per agent run, holding only what is specific to that run.
  • {{page:reviews}}/<Epic> — review records, one per reviewed candidate, naming the exact SHA.
  • {{page:library}}/Universal prompts — prompts reused across tasks and epics: {{page:builderContract}}, {{page:reviewerContract}}, {{page:orchestratorLoop}}, {{page:convergeLoop}}.
  • {{page:library}}/Skills — reusable procedures an agent loads on demand (task, pr, review, handoff).
  • Engineering Standards — coding and process standards, including this page.
  • {{page:issues}} — work that is not an epic leaf, filed in its buckets (see Issues below).
  • {{page:documentation}} — the published documentation, owned by the documentation pipeline.

Naming

Prompt — stage N <role> (<scope>) · Plan — … · Handoff — stage N <role> (PR #n) · Review record — stage N <what> (<sha or PR>) · Delivery log — <Epic>.

Linking rules

  • Link with page mentions, not pasted URLs. In a document: <a class="mention" data-mention-type="page" data-page-id="PAGE_ID">@Title</a>. In channels and plain text: @[Title](PAGE_ID:page). Both are indexed on save and produce backlinks.
  • Direction is specific → general. A task mentions its plan, prompts, handoffs and reviews. A task prompt mentions the universal prompt it uses. A review mentions the tasks, prompt and handoff it covers.
  • Universal prompts and skills never mention a task, plan, prompt or review. They are reused; their backlinks show who uses them.
  • Every phase and leaf page ends with a "Related pages" block. The orchestrator adds each artifact to it when the artifact is created. Adding links is not a criterion change; criteria text is never edited this way.
  • Every PR description, written with the /pr skill, links its tasks, plan and prompt, with every task code written in full (the documentation pipeline reads task codes from the PR title, branch and body, and classifies the merge from the conventional-commit title). Every PR also carries a comment linking all of its related pages: prompt, plan, handoff and every review record. Review verdicts are also posted as a PR comment.

Who writes what

  • The orchestrator writes the task prompt page first, then spawns the agent with pagespace pages read <promptPageId>. A prompt changed mid-run is edited in place so history shows what the agent was told.
  • Builders publish their handoff; reviewers publish their review record. Reviewers run in the builder's worktree and leave it clean.
  • Every agent publishes its own artifact pages and keeps its own tasks current up to In Review. No agent edits the criteria or scope of a task delegated to it. A merged task moves to Merged automatically; Done is granted from an independent review record, never by the agent that did the work. Criteria, specs and scope change only with the owner's recorded approval.
  • A decision an agent makes on the owner's behalf is recorded with bun decision:record in {{page:pendingDecisions}}; it stays open until the owner moves it to Confirmed or Overruled.
  • Gate logs and traces stay with CI or the PR and are linked from the record. Secrets and env material are never uploaded.

Issues

Defects and review findings that are not part of an open leaf go in the {{page:issues}} task list at the drive root, filed in one of its buckets ({{page:bugs}}, {{page:testCoverage}}, {{page:agentTooling}}, {{page:docDrift}}, {{page:userFeedback}}; {{page:backlog}} and {{page:pendingDecisions}} live there too), never in GitHub Issues. The test is whether an open leaf owns it: if one does, the finding is a follow-up leaf under that phase regardless of merge state. Title ISSUE-n — Given X, should Y; body records origin (PR, review record, reporter), why, and acceptance criteria; the Related pages block links the origin. An issue is closed by a PR that names it, or promoted to an epic leaf when it grows into feature work.

Why this list exists: findings that were out of scope for the PR under review used to live only in review prose and were lost the moment the PR merged, so bad code persisted. Therefore filing is an obligation, not an option — whoever observes it (reviewer, builder, orchestrator) files the leaf or issue in the same session, and a review record is not finished while any unfixed finding lacks a page id. The list is read at two fixed points: the orchestrator scans every bucket before every stage and carries relevant issues into the prompt as known debts, and no phase or epic closes while an issue it produced is untriaged (promoted, scheduled, or deferred by the owner with a reason).
